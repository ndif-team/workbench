1Summary

Patch Lens lets a researcher drag one residual-stream cell from a source prompt into a target prompt and watch the network's prediction change. Algorithm Hypothesis does the same for a hypothesized algorithm. The researcher draws the algorithm directly on the grid: each variable lives in a cell (layer, token), arrows show which tokens and variables it reads, and a function computes its value. Dragging a cell from the source grid onto the target grid then runs an interchange intervention on the algorithm and shows the counterfactual output it predicts.

The running example is entity binding. For the paper's Figure 1 inputs, an interchange intervention on the binding information at the last token yields three different counterfactual outputs, depending on which algorithm you believe: positional → jam, lexical → ale, reflexive → pie. The tool's first job is to make that divergence easy to build and see. Its long-term job is to put the algorithm's counterfactual output next to the network's, cell for cell.

Under the hood an algorithm is a causalab causal model plus a placement. Section 4 gives the semantics. Sections 5–7 cover the three surfaces (editor, cell intervention, token sweep). Section 10 is the build plan.

3Background

3.1Running example: three ways to retrieve a bound entity

Gur-Arieh, Geva and Geiger (2025) study how a model answers What does Tim love? after reading a list of bound pairs. They formalize three algorithms, which they call mechanisms. Each has one intermediate variable at the last token, and each yields a different counterfactual output when that variable is swapped in from the source input.

InputTextOutput
TargetAnn loves ale, Joe loves jam, Pete loves pie, Tim loves tea. What does Tim love?tea
SourceJoe loves ale, Ann loves pie, Pete loves jam, Tim loves tea. What does Ann love?pie
AlgorithmVariable at the last tokenHow the answer is retrievedCounterfactual output
𝒫PositionalP, the position ID of the recalled nameThe entity that carries position ID PP ← 2 → jam
ℒLexicalL, the recalled name itselfThe entity bound to the name LL ← Ann → ale
ℛReflexiveR, a pointer to the answer entityDereference R in context; nothing if the entity is absentR ← pie → pie

The names are the algorithm's special tokens. Position ID numbers them in order of first appearance and stores each as a position ID : name pair, so Ann is 1:Ann. In the positional algorithm, each name's pair is computed above the name (pos1 = 1:Ann), its ID is copied onto the bound entity (id1 = 1, with KeyOf), and the entity is bound to it (bind1 = 1:ale). When the question recalls a name, Position ID gives it its first mention's ID, so the second Tim is 4:Tim (q_pos). The last token takes the ID (P = 4) and retrieves the entity bound to it. The lexical and reflexive algorithms bind name : entity pairs instead.

Two more experiments from the paper map directly onto the visualizers. Figure 2 sweeps the last token across layers and finds a window (layers 16–18 in gemma-2-2b-it) where the swapped binding information decides the counterfactual output; after it, the answer itself gets copied. Section 3.4 uses a source input with cod, an entity the target never mentions, to separate the reflexive pointer from the answer: the pointer can't be dereferenced, so the reflexive algorithm outputs nothing. The paper's Section 4 combines the three into one model (their Eq. 2). Here the fourth algorithm, Mixed, is their exact union: every variable of each, with each mechanism's answer computed separately and the three answers combined linearly at the last token.

The mockups below use Figure 1's 17 word tokens, with the commas, period and “and” dropped. The editor in workbench keeps punctuation as tokens (21 abstract tokens; 22 for gemma-2-2b-it, which adds <bos>).

3.2What we build on

  • causalab (causalab/causal). @mechanism definitions compile to a CausalModel whose variables are named nodes with equations. CausalTrace caches values and applies interventions (trace[var] = value, intervene_many). Models carry print_pos, a per-variable layout, which we fill with the grid placement. The module uses only the Python standard library, which is what makes Pyodide possible (§9.2).
  • Patch Lens (workbench). The patch-lens route wraps CausalMediationExplorer from edulogitlens: two prompts, two grids, drag a source cell onto a target cell, a curved arrow, a result grid with the affected region tinted purple, a shared toolbar (zoom, layer step, synced scroll), and a persisted spec {srcLayer, srcTokenPos, tgtLayer, tgtTokenPos}. We copy its gestures, its colors (source cyan, target pink, counterfactual purple) and its persistence shape. Its grid cells show logit-lens readouts; ours show the algorithm's variables instead.
  • The entity_binding task in causalab models the positional algorithm, with input generators and named token positions such as last and g{g}_e{e}_last.

4Placed algorithms

An algorithm is a causal model whose variables each live in a cell of the grid. The placement is part of the hypothesis: “the model computes q_pos at layer 3, above the query token.” Arrows, interventions and sweeps all follow from the placement and four rules.

4.1The grid

  • Tokens run across and layers go up, as in the paper's Figure 1. The token labels form an Emb row at the bottom.
  • An algorithm's grid is either abstract (word tokens, 8 layers) or a model's (that model's tokenizer and layer count). The model grid is gemma-2-2b-it, with 26 layers; the walkthrough uses the abstract grid, where interventions are easier to see. A model grid uses only the tokenizer; nothing runs the model. A layer step of N shows every N-th row, and each shown row stands for the layers up to the next one.
  • Clicking a token label focuses it, and unfocused tokens can be hidden. Focus only changes the view, never the algorithm.

4.2Variables and types

A variable has a name (a Python identifier), a cell, a type, a function (a built-in primitive or a Python function), and named arguments. Each argument holds one or more references to tokens or earlier variables. Exactly one variable, the output, sits at the last layer and the last token. A cell can hold several variables, as in Figure 1, where one cell carries positional, lexical and reflexive information.

Types. Every value has one of four types, and the type sets the variable's glyph, after the paper's Figure 1:

TypeGlyph and an example valueIn the examples
position2id1–id4 and P in the positional algorithm: a position ID
stringaleTokens, q_key, L, R, answer
int3Counts and other numbers (a constant, or Python)
key : value:1:alepos1–pos4, q_pos and bind1–bind4 (position : string) in the positional algorithm; bind1–bind4 (string : string) in the others

A pair's key and value are typed, so pairs nest: (position : string) : string, drawn (:):. Tokens are strings. A primitive's type follows from its arguments (§4.6): Pair applied to a position and a token is a position : string. A Python function declares its type in the panel. Position IDs and ints are kept apart, so an int can't be used where a position ID is expected (Q19).

Color and tags. Glyphs carry the type, so variables are black (white in dark mode) by default. Each variable can also have a color (a palette color or any other) and free-form tags, both for the researcher's own bookkeeping; neither affects what it computes. Each of the paper's examples colors a variable by the one algorithm it serves: positional indigo, lexical green, reflexive amber. Variables several algorithms share, the name bindings, stay black, as does Mixed's combined answer, so the three examples' colors together are the mixed example's. Only the editor shows colors; the intervention view draws every variable black.

Special tokens. An algorithm designates some token positions as special, such as the names in the template. Click Mark in the Algorithm panel, then the token labels; special tokens are underlined. On the paper's prompts, the names are marked from the start, and follow the prompt while the algorithm is empty and they haven't been marked by hand. Every Position ID reads the special tokens up to its own cell, and follows when they change.

4.3Residual semantics

In a transformer, what a layer writes at a position stays in that position's residual stream for every later layer. Variables get the same lifetime. A variable is born in its cell and carried up its column until just below the last variable that reads it. Its arguments are known, so this span is known exactly. The editor marks it with dashed copies of the variable, as Figure 1 repeats its glyphs up each column.

Arrows leave from the recall point. A variable reads each argument from the layer just below itself, so its arrow starts at the copy of the argument in that row, or at the top of the argument's span when the reader sits higher. bind1's arrow into answer at L7 starts from bind1's dashed copy at L6, not from L2 where bind1 was computed. A token's arrow rises up the token's column to the same row and bends there. The arrows then show where each value is used, which is also where an intervention on it starts to matter.

Interventions follow from spans. An interchange intervention on cell (l, t) replaces every value whose span covers (l, t). Variables above layer l read the source's value; those at or below l keep the target's. Here is the positional algorithm's last-token column:

This is what makes the token sweep (§7) meaningful: the layers where an intervention changes the counterfactual output are exactly the span of the variable that carries it. It also compiles cleanly to causalab. Each layer a value is carried through becomes a relay node (P__L6 = V(P)), and each variable reads the relay one layer below itself. An intervention on (l, t) is then an ordinary causalab intervention on the nodes at layer l. That is how algorithm_hypothesis compiles algorithms (§9.3).

4.4Rules

  1. Arguments come from strictly lower layers.
  2. Arguments come from tokens at or before the variable's own token. Together with rule 1, an algorithm can only go up and to the right, like a transformer (Q4).
  3. The output sits at the last layer and the last token.
  4. Tokens are inputs born on the embedding row and carried like variables, so interventions on the embedding layer are allowed (Q5).

Rules 1 and 2 also make cycles impossible. The editor enforces all four: it refuses an argument, a move or an output that breaks one, and says why.

4.5Moving variables

Dragging a variable to another cell changes only where it lives; its name, function and arguments stay the same. The move is checked against the rules from both sides. The variable's arguments must still be below it and to its left, and every variable that reads it must still be above it and to its right. Variables are anchored to token positions in the template (Q1), so dragging is also how to fix a variable that landed on the wrong token after the prompt changed.

Copy replaces Token identity, and Retrieve replaces Lookup (build the pairs with Pair) and Dereference (match by value). A reference whose type doesn't fit is refused when it's clicked, with the reason. For example, the query token, a string, can't retrieve from the positional bindings, whose keys are position IDs: “pairs: bind1 is position : string, but this argument needs string : any type (V).”

Every primitive is a Python function in algorithm_hypothesis.primitives, and the panel shows its source, with the current options filled in as defaults (Q8). Here is Position ID:

def position_id(token: str, specials: list[str]) -> Pair[Position, str]:
    """The token's position ID, stored as position ID : token. Each distinct
    special token (such as a name) gets the next ID in order of first
    appearance, so a name mentioned again gets its first mention's ID.
    `specials` are the special tokens up to this one; a possessive ('s) is
    ignored when comparing them."""

    def name(t):
        return str(t).strip().split("'")[0]

    ids = {}
    for t in specials:
        if t is not None:
            ids.setdefault(name(t), len(ids) + 1)
    if token is None or name(token) not in ids:
        return None
    return Pair(ids[name(token)], token)

Position ID reads the special tokens of the current input, not the template, so in the source prompt (“Joe loves ale, Ann loves pie, …”) Ann is 2:Ann. Its specials are ordinary references, so they draw arrows, extend the tokens' spans, and can be intervened on like any other argument.

Double-click the code to edit it. The variable becomes a custom Python function that starts from the primitive's source, renamed compute, and keeps the same arguments and type. A custom function's arguments are the parameters of compute, one per named argument; an argument with several references arrives as a list, and a parameter named template receives the template's tokens. Its type is declared with a type picker, which nests for pairs. It runs in the browser (§9.2). Values can be single values or distributions; the grid always shows one value, the top one for a distribution (Q10).

For a primitive, type is inferred and saved for readers of the file; for a custom function it is the declared type. 5Editor

The editor (Edit) is where an algorithm gets built. This is the flow as implemented:

  1. Prompt → grid. Type a prompt or pick one from Inputs (saved with the algorithm, or examples), and the grid builds from its tokens. Choose an abstract or a gemma-2-2b-it grid. Layer step and token focus keep large grids readable.
  2. Mark the special tokens, such as the names, that Position ID numbers (Algorithm panel, Mark).
  3. Click a cell → New variable. The panel docks on the right and the cell is outlined. Clicking another cell moves the new variable there.
  4. Name it and choose its function. A primitive shows its Python source; double-click it to make it your own function, edited in CodeMirror and run in the browser. The Type row shows the type the variable will have, or, for a custom function, lets you declare it. Give it a color and tags if you like.
  5. Fill its arguments by choosing a slot and clicking tokens or variables in the grid. Each slot shows its name and type, and each reference shows its type's glyph and draws an arrow into the cell. A reference that breaks a rule or doesn't fit the slot's type is refused, with the reason.
  6. See its value on the current prompt as you build it. A custom function's value appears once Python has run it, or its error appears in place.
  7. Mark the output at the last layer and last token. Until one exists, the status bar says what's missing.
  8. Drag variables to move them, edit or delete them from the grid or the variable list, and switch prompts to see their values on other inputs. A new variable is named after its function (PosID1, Copy1, …), until you type a name.
  9. Copy a variable (Copy in its panel, or Ctrl/⌘ C) and paste it into another cell (Paste here, or Ctrl/⌘ V), or Alt-drag it (Option on a Mac). The copy keeps its function, custom code, arguments, type, color and tags, takes the next free name, and flags any argument that breaks a rule at the new cell.
  10. Save it when it's complete. Edits autosave as a draft; Save stores the version other views compare against, and the panel shows “Not saved yet”, “Saved” or “Unsaved changes” (with Revert). New starts another algorithm, and Open lists saved algorithms and drafts, or opens one from a JSON file. Export gives JSON that algorithm_hypothesis compiles to causalab.

Design notes.

  • The glyph follows the type (§4.2), so a position : string binding reads ◇ : ● wherever it appears: in the grid, the argument slots and the variable list. Color is the variable's own.
  • Arrow density. Drawing every read gets cluttered fast; the positional algorithm alone has 27. The editor always draws variable-to-variable arrows, and draws token reads only when the token is within two positions or the variable is selected. “All arrows” and “No arrows” are one click away.
  • Dashed copies show spans, so you can see where a variable can be intervened on before opening a visualizer.
  • Workbench patterns only: a docked panel with the standard header, the shared Select, Input, Checkbox, Popover and DropdownMenu primitives, toasts for refused moves, and destructive actions confirmed in a popover.

6Visualizer 1: cell intervention

Two inputs, two grids, one drag: the Patch Lens gesture applied to the algorithm. Dropping a source cell on a target cell runs an interchange intervention. A third grid, the counterfactual, tints every changed value purple, and the summary shows the counterfactual output next to the target's own output.

It differs from Patch Lens in two ways. The cells hold named values rather than logit-lens readouts, so the summary can say exactly what was swapped (P: 4 → 2) and why the output moved. And because an intervention costs microseconds, the summary also runs the same intervention on every saved algorithm. That table is the paper's argument at a glance: one drag, three counterfactual outputs.

Only variables with the same name are swapped (Q9). A drag between cells that share no variable is refused, with a message.

Built in P4. In workbench, Intervene switches the chart to this view, with every variable in black (colors are for editing). The source and target inputs come from the algorithm's saved inputs or the examples, and a button swaps them. The three grids scroll together, so the intervention arrow (cyan dot at the source, pink at the target) stays attached. Clicking a cell picks it, which also works on touch screens; the token row is the embedding layer. The table runs the intervention on this algorithm, and on the saved version of every saved algorithm in the workspace with the same grid, with “no swap” where the cells share no variable. The inputs and the intervention are saved with the chart, so a reload restores them. Custom functions run in Python here too.

7Visualizer 2: token sweep

Drag a source token onto a target token. For each layer, from the embedding layer to the top, the tool runs an interchange intervention on whatever the algorithm carries at that (layer, token) and records the counterfactual output. The result is a layers × 1 strip per algorithm: the algorithm's version of the paper's Figure 2.

When source and target have the same tokens, Full grid runs every position at once (token t into token t). That gives a layers × tokens map of counterfactual outputs per algorithm, which we will later lay over Patch Lens's heatmap.

Reading the default sweep, “?” into “?”:

  • Embedding layer to L4: nothing lives at the last token yet, so the counterfactual output stays tea.
  • L5–L6: the binding window. Each algorithm predicts its own entity: jam, ale, pie. The mixed algorithm splits between ale and pie.
  • L7: the answer itself is swapped, so every algorithm outputs pie.

Now drag “Ann” (14) onto “Tim” (14). From the embedding layer to L2, the intervention swaps the token itself, so every algorithm answers as if asked about Ann (ale). At L3–L4 it swaps what the query token has already retrieved, and the algorithms separate again.

Built in P5. Sweep is the chart's third mode.

  • Picking the token: drag a source token onto the same token of the target, or click a token. Sweeps compare the same position (Q16), so a drop on a different token is refused with a message.
  • Strips: each algorithm (this one and the saved ones) gets a strip of counterfactual outputs from the top layer down to the embedding row.
  • Colors: each output keeps its color in every view; the target's own output is gray, faded cells had nothing to swap, and ∅ is hatched.
  • Summary: the side panel says where each algorithm's output changes, e.g. “jam at L5–L6 · pie at L7”.
  • Full grid: maps every position at once when the inputs have the same number of tokens.

Design notes.

  • Color encodes the counterfactual output, not the algorithm. The legend says which algorithm predicts each value for the current inputs. Unchanged is gray; ∅ is hatched.

8Toward side by side with Patch Lens

The end state is one screen where a single drag runs an interchange intervention on both the algorithm and the network, with the two counterfactual outputs side by side. Three decisions keep that open:

  • Same grid. On a model grid, the algorithm's columns are that model's tokens and its rows are that model's layers, so cell (l, t) means the same place in both tools.
  • Same gesture and record. An intervention is stored with Patch Lens's fields.
  • Same tokenizer path. Model grids tokenize with workbench's own tokenizer action, as Patch Lens does.

Three ideas to explore once v1 ships. These are wireframes, with no data behind them:

Twin grids

The algorithm grid above the network grid for the same prompt. One drag intervenes on both. The result row shows the network's counterfactual top token next to the algorithm's counterfactual output.

Agreement map

Run the full-grid sweep in both and mark each cell where the network's counterfactual output matches the algorithm's. Over a dataset this is interchange intervention accuracy per cell, which causalab already computes.

Placement hints

Use the agreement map to suggest moving a variable to the layers where agreement peaks, for example aligning P's span with layers 16–18 of gemma-2-2b-it.

9Architecture

9.1In workbench (P2–P4, built)

  • Route. A chart type, algorithm-hypothesis, at app/workbench/[workspaceId]/algorithm-hypothesis/[chartId]/. AlgorithmHypothesisArea is the container: it reads the route, loads the chart and its algorithm, autosaves, and routes grid clicks. In Intervene mode it hands over to InterventionView, a second container that tokenizes the inputs and runs the interventions. AlgorithmGrid (an editing mode and a read-only mode), VariablePanel, AlgorithmPanel and GridToolbar are presentational.
  • Engine. lib/algorithmHypothesis/ holds the TypeScript engine: types and their inference, primitives (with their Python sources, generated from the golden file), spans, evaluation, validation, moves and interchange interventions. It evaluates on every edit and runs in microseconds. A golden test keeps it in line with the Python package cell for cell.
  • Python. python.ts runs custom functions in a Pyodide worker started from a Blob URL, so neither the bundler nor a static file is involved. The engine stays synchronous: a Python variable is a cached result, or “pending” while its call is queued, and components evaluate again when results arrive (§9.2).
  • State. The algorithm is server data, edited as a local working copy that autosaves half a second after each change. The prompt, view settings, mode and intervention autosave to the chart row, like Patch Lens's prompts and patch.

9.2Where the algorithm runs

Decision (Q6): primitives run in the TypeScript engine, and custom Python functions run in a Pyodide worker in the browser, so user-written Python is sandboxed and never runs on the server.

The worker runs one call at a time: a function's source and its arguments' values go in as JSON, and a value or an error comes out. It loads a small bundle, golden/python_runtime.json, holding values, vartypes, primitives and runtime from the package, and no causalab. runtime.strip_function prepares a function the same way the causalab compiler does, so it behaves the same in both places. The runtime checks that the returned value fits the declared type, and an error names its line. A call that runs past 3 seconds is stopped and the worker restarts. Pyodide (about 10 MB) loads from a CDN the first time a custom function runs. NEXT_PUBLIC_PYODIDE_URL can point it at another copy.

The spike checks both paths in Node: causalab and the package in Pyodide, compiling all five golden algorithms and rerunning every full sweep; and the runtime bundle on its own, running the golden Python calls. Latest run, 3 October:

StepTime
Load Pyodide (local files; a browser adds a cached ~10 MB download)1.6–4.3 s
Compile one algorithm to a CausalModel0.13–0.37 s
1,000 interchange interventions (compiled model)0.33–1.5 s

Times vary about threefold between runs on this machine, Pyodide's own load included. In the browser, the first custom function's value appeared about 1.8 s after the page asked for it; later calls take milliseconds. Token and pair values are immutable and shared between causalab's trace copies; copying them cost 2–3 ms per intervention before that fix.

9.3The Python package (P1, built)

Decision (Q12): algorithm_hypothesis lives in this project (algorithm-hypothesis/python) and depends only on causalab.causal. The public causalab repo is synced from internal development, so the code should move upstream through that route once the API settles. It loads schema-v3 JSON, checks the rules and types, generates a @mechanism with relay nodes, and runs interventions and sweeps on the compiled CausalModel:

from algorithm_hypothesis import compile_algorithm, tokenize_abstract

compiled = compile_algorithm("positional.json")   # exported from the editor
target = tokenize_abstract("Ann loves ale, Joe loves jam, Pete loves pie, Tim loves tea. What does Tim love?")
source = tokenize_abstract("Joe loves ale, Ann loves pie, Pete loves jam, Tim loves tea. What does Ann love?")

result = compiled.interchange_intervention(source, target, (5, 20), (5, 20))
result.output            # "jam", the counterfactual output
result.counterfactual    # the intervened causalab trace
compiled.model           # the causalab CausalModel
print(compiled.source)   # the generated @mechanism, with P__L6 = V(P, ...) relays

9.4Persistence

Decision (Q11): a workspace-scoped algorithms table, mirrored in schema.pg.ts and schema.sqlite.ts. Each row holds the working copy (definition, autosaved on every edit) and the version saved as complete (saved_definition and saved_at, empty for a draft). A chart stores its algorithm's id, the prompt and view, the mode, and each view's inputs and settings (the intervention, the sweep, the walkthrough), so a reload restores them. Copying a chart copies its algorithm, as a draft.

12Decisions and open questions

All questions so far are decided.

Q1How do variables carry over to other prompts?

Decided: prompts are templated to have the same tokens, so variables are anchored by token index. Users drag a variable if it landed on the wrong token. Primitives that detect positions automatically come later.

Q2Does a variable live in one cell, or in a span up its column?

Decided: a span, ending just below the last variable that takes it as an argument (§4.3).

Q3Which way should the grid face?

Decided: tokens across, layers going up, as in the paper. The editor has only this orientation.

Q4Enforce the causal mask and strict layer order?

Decided: yes. Algorithms are autoregressive: arguments only come from below and to the left.

Q5Can tokens themselves be swapped?

Decided: yes, as interventions on the embedding layer.

Q6Where does the algorithm run?

Decided: Python in a Pyodide worker (spike in §9.2), primitives in the TypeScript engine, with a golden file keeping the two in agreement. Built in P3: the worker runs one custom-function call at a time, and the TypeScript engine runs everything else, interventions included.

Q7Model tokens and layers, or abstract ones?

Decided: both. The demo used gemma-2-2b-it until 5 Oct; the walkthrough now uses the abstract grid, where interventions are easier to see. During development nothing runs gemma-2-2b-it: the tool only borrows its tokenizer and layer count.

Q8Flat argument list, or typed slots per primitive?

Decided: named argument slots, Python-style. A slot takes one reference or a list. Revised 2 Oct: slots are typed (string, int, position ID, key : value), with type variables for generic primitives such as Retrieve, and a primitive's Python source is shown and can be edited (§4.6).

Q9What happens when an intervention connects two different cells?

Decided: only variables with the same name are swapped. If two cells share none, the intervention is refused with a message.

Q10Is the output a value or a distribution?

Decided: both are supported. Visualizations show a single value, the top one for a distribution.

Q11Where are algorithms stored?

Decided: a workspace-level algorithms table that charts reference (§9.4).

Q12Where does the Python package live?

Decided: in this project for now, depending only on causalab.causal; upstream into causalab through internal development once the API settles (§9.3).

Q13Which words?

Decided: inputs are source and target. Outputs after an intervention are counterfactual, and that word never refers to an input. Also variable, algorithm (or mechanism) and (interchange) intervention (§3.3).

Q14More than one intervention at a time?

Decided: one in v1; multi-variable and multi-source interventions are Phase 8.

Q15What is it called?

Decided for now: Algorithm Hypothesis. Patch Lens is named for the logit lens in its cells, which this tool doesn't use. The name is still open to workshopping.

Q16Token sweeps between different positions

A variable lives in one column, so under the same-name rule a source token dragged onto a different target token shares no variables.

Decided 3 Oct: sweeps compare the same position only; a drop on a different position isn't allowed, and the tool says why. Pairing variables across positions can return with Phase 8.

Q17Where do position IDs come from?

Until 3 October, Position ID read group numbers from the template, so it depended only on position. Now it numbers the algorithm's special tokens, as they appear in the current input, in order of first appearance. A repeated name gets its first mention's ID.

Decided 3 Oct: from the special tokens, stored as position ID : token (§4.6).

Q18Abstract grids keep punctuation as tokens

The paper's figure drops commas and periods; the editor's abstract tokenizer keeps them, so abstract grids line up with model grids.

Decided 3 Oct: keep punctuation in the columns. A user can hide those columns with focus, or leave punctuation out of the prompt.

Q19Is a position ID a kind of int?

Decided 3 Oct: no. A position ID is its own type, like a pointer address: the tool does no arithmetic on position IDs, and an int can't stand in for one.

Q20Special tokens by position, or by value?

Decided 3 Oct: designated by position in the template, as built (§4.2).

Q21Intervention view: a mode of the chart, or a chart of its own?

Decided 3 Oct: a mode. The chart switches between Edit, Intervene and Sweep; saving algorithms (§5) makes the comparison across algorithms explicit.
